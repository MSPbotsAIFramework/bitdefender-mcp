## Requirement understanding

One line: Manage endpoint protection policies and review security events via Bitdefender GravityZone.

The ticket asks for a new MCP connector so Agent-platform agents can work with a tenant's
Bitdefender GravityZone deployment: look at the endpoint-protection policies that are configured,
and review/triage the security events (incidents) GravityZone has raised. The ticket body is a
one-paragraph marketing-style blurb plus a link to the product's listing on the Conduit/WYRE AI
plugin marketplace (`https://conduit.wyre.ai/plugins/bitdefender`). Per prior tickets in this
pipeline (e.g. PRD-21269, PRD-21278), that marketplace page is a generic template and not vendor
API documentation — it was used only to confirm the product name, not as a source of capabilities
or contract details.

### Vendor API confirmed

Bitdefender publishes a real, public Control Center / GravityZone API (not gated behind a partner
portal):

- Overview and API index: `https://www.bitdefender.com/business/support/en/77212-125277-public-api.html`
- Full reference: *Bitdefender Control Center API Guide* (publication date 2019-03-29, still the
  current reference — corroborated by the live Control Center changelog showing method additions as
  recent as 2026-10, e.g. `setPolicyModulesState` under Policies, new `getEndpointsList` /
  `getNetworkInventoryItems` response fields): `https://www.bitdefender.pl/download/Bitdefender_Control_Center_API_Guide_On-premise_version_enUS.pdf`
- Protocol: JSON-RPC 2.0 over `HTTP POST`, `Content-Type: application/json`, one URL per API
  category: `CONTROL_CENTER_APIs_ACCESS_URL/v1.0/jsonrpc/<service>` (API Guide p.2-3).
- Auth: `HTTP Basic Authentication` — `Authorization: Basic base64(<api_key>:)` (API key as username,
  empty password) — API Guide p.5.
- Rate limit: 10 requests/second per API key; excess returns HTTP 429 — API Guide p.2, p.6.
- Services relevant to this ticket: **Policies** (`getPoliciesList`, `getPolicyDetails` — API Guide
  §2.6, p.72-74), **Network** (`getEndpointsList`, `getManagedEndpointDetails`,
  `getNetworkInventoryItems` — API Guide §2.4, p.33-49), **Incidents** (`getIncidentsList`,
  `getIncident`, `changeIncidentPriority`, `assignIncident`, `createIsolateEndpointTask`,
  `createRestoreEndpointFromIsolationTask` — API Guide §2.10, p.142-147, with `getIncident` /
  `getIncidentsList` living on newer `v1.1`/`v1.2` incident endpoints per the live product page).

## Product design

### Goals / Non-goals

**Goals**

- Give agents read access to a tenant's GravityZone endpoint-protection **policies**: list them,
  inspect one in detail.
- Give agents read + triage access to a tenant's GravityZone **security events (incidents)**: list
  them, inspect one in detail, change an incident's priority, (re)assign an incident, and take the
  two endpoint-protection response actions GravityZone exposes for an active incident — isolate an
  endpoint and restore it from isolation.
- Give agents enough endpoint-inventory visibility (list endpoints, endpoint detail) to resolve the
  endpoint ids that the incident and isolation tools need.
- Ship this as a standard MSPbots Connector: credentials read only from request headers, one
  GravityZone API key per tenant, no OAuth, no server-side state — matching the credential-form
  pattern the platform already uses for comparable security vendors (SentinelOne).

**Non-goals (out of scope for this ticket)**

- Creating or editing policies, or assigning a policy to an endpoint/group — GravityZone's
  documented Policies API is read-only (`getPoliciesList`, `getPolicyDetails`); there is no
  policy-assignment method in the confirmed API Guide. Treated as a scope decision, not a gap (see
  "Decisions made by DEV01").
- Company/account/licensing administration, package/installation-link management, custom endpoint
  groups, scan-task scheduling, quarantine item management, push-event (webhook) configuration — the
  ticket asks for policy visibility and event review, not full GravityZone console administration.
  Flagged as follow-up scope if a future ticket asks for it.
- Any `mcp-service-gateway` or platform UI change — none is needed; the connector becomes visible in
  the Library once registered via `vendor-register`.

### Acceptance criteria

- **AC1**: Given a tenant's GravityZone API key is supplied via the credential header, when the agent
  calls `bitdefender_list_policies`, then the tool returns the tenant's configured policies (id,
  name), paginated, sourced from GravityZone's Policies API.
- **AC2**: Given a valid policy id, when the agent calls `bitdefender_get_policy_details`, then the
  tool returns that policy's full configuration as GravityZone's `getPolicyDetails` returns it.
- **AC3**: Given a tenant's API key, when the agent calls `bitdefender_list_endpoints`, then the tool
  returns the tenant's managed endpoints (id, name, status), paginated, from GravityZone's Network
  API.
- **AC4**: Given a valid endpoint id, when the agent calls `bitdefender_get_endpoint_details`, then
  the tool returns that endpoint's detail (assigned policy, protection status) from GravityZone.
- **AC5**: Given a tenant's API key, when the agent calls `bitdefender_list_incidents` with no
  filters, then the tool returns the tenant's open security incidents (id, name, priority, status),
  paginated, from GravityZone's Incidents API.
- **AC6**: Given a valid incident id, when the agent calls `bitdefender_get_incident`, then the tool
  returns that incident's detail (affected endpoints, timeline summary) from GravityZone.
- **AC7**: Given a valid incident id and an allowed priority value, when the agent calls
  `bitdefender_change_incident_priority`, then GravityZone's `changeIncidentPriority` is invoked and
  the tool reports success or the vendor's rejection reason.
- **AC8**: Given a valid incident id and one or more GravityZone user ids, when the agent calls
  `bitdefender_assign_incident`, then GravityZone's `assignIncident` is invoked and the tool reports
  the resulting assignment.
- **AC9**: Given a valid endpoint id under investigation, when the agent calls
  `bitdefender_isolate_endpoint`, then GravityZone's `createIsolateEndpointTask` is invoked, the tool
  reports the created task id, and the tool is marked destructive (`destructiveHint`).
- **AC10**: Given a previously isolated endpoint id, when the agent calls
  `bitdefender_restore_endpoint_from_isolation`, then GravityZone's
  `createRestoreEndpointFromIsolationTask` is invoked and the tool reports the created task id.
- **AC11**: Given the credential header is missing, when any `bitdefender_*` tool is called, then the
  tool returns HTTP 401 listing the required header(s), never a 500.
- **AC12**: Given GravityZone returns a JSON-RPC error (e.g. `-32602 Invalid params`) or an HTTP
  error (401/403/429), when any `bitdefender_*` tool receives it, then the tool returns the
  structured error envelope with the matching `code` (`invalid_argument` / `unauthorized` /
  `rate_limited`) instead of raising an exception or returning a raw 500.
- **AC13** (multi-tenant isolation): Given two different tenants' API keys are used in two
  concurrent requests to the same running service instance, when each calls
  `bitdefender_list_policies`, then each response reflects only its own tenant's data and no
  credential or response data crosses between the two requests.
- **AC14**: Given GravityZone's documented limit of 10 requests/second per API key, when the service
  issues calls faster than that, then it backs off per `Retry-After` / a bounded retry policy and
  surfaces `rate_limited` rather than hanging or crashing.

### Open questions

- **Not blocking** — GravityZone's public API has no policy-assignment method in the confirmed API
  Guide. If assigning a policy to an endpoint/group turns out to be needed, it would require either
  a newer API method not covered by the 2019 guide (the live changelog shows the API keeps
  evolving — e.g. `setPolicyModulesState` was added later) or a scope conversation with the vendor.
  Proceeding on the assumption that "manage policies" means visibility, not authoring, for v1; if
  that assumption is wrong this ticket should be reopened with the missing capability named
  explicitly (per `references/mcp-track.md` 2.1, "capability not covered by the tool table" is itself
  a valid future ticket).

## Tech design

### Conclusion

Build the first version of `MSPbotsAIFramework/bitdefender-mcp` per the vendor-mcp-development SOP
(Python 3.12 + uv + FastMCP, Streamable HTTP, stateless, credentials from headers). Ten tools across
three GravityZone API categories (Policies, Network, Incidents) implement the twelve ACs above.
Since the repo currently has nothing but a skeleton README, this is a from-scratch build on the
already-created repo, not a modification of an existing tool set.

### Where the current implementation lives

Nowhere yet — `README.md` is the only file in the repo (`README.md:1-2`, commit `28c9850`). No prior
MCP implementation, server code, or tests exist to extend.

### Option analysis

- **JSON-RPC client library vs. hand-rolled `httpx` calls**: use `httpx.AsyncClient` directly. The
  vendor API is a thin, uniform JSON-RPC 2.0 shape (one `{jsonrpc, id, method, params}` POST per
  call); a dedicated JSON-RPC client dependency would add a layer for no real benefit over three
  helper functions (build request, send, map error). Matches SOP guidance to prefer the smallest
  dependency that does the job.
- **Credential transport**: `X-Bitdefender-Api-Key` header, consumed per-request and turned into the
  `Authorization: Basic base64(<key>:)` header the vendor expects, inside the request handler — never
  stored, never put in an env var. A second, optional header `X-Bitdefender-Base-Url` carries the
  tenant's Control Center Access URL (defaults to `https://cloud.gravityzone.bitdefender.com/api`
  for Bitdefender's own cloud; on-prem/custom Control Center installs have a different Access URL
  per the API Guide p.2). Considered hardcoding the cloud URL only — rejected because the API Guide
  treats the Access URL as a per-tenant value from the start, and on-prem GravityZone is common
  enough in the MSP space that hardcoding would silently break those tenants.
  pydantic-settings — `SettingsConfigDict(extra="ignore")`. Rejected a server-side default stored in
  config instead of a header: that would violate the "credentials/config only from headers, no
  server-side per-tenant state" rule for MCP connectors.
- **Pagination**: pass GravityZone's own `page` / `perPage` straight through as tool parameters
  (default `per_page=50`, hard cap `per_page<=200`), returning the vendor's own `page` / `pagesCount`
  / `total` alongside `items`. Rejected building a second, different pagination convention — the
  vendor's shape is already exactly what the SOP asks for (bounded, cursor-free, token-economical).

### Reuse & cleanup

- **Reuse**: FastMCP (stateless HTTP transport, tool registration, hint annotations), `httpx`
  (async client, built-in timeout/retry primitives), `pydantic-settings` (header-tolerant config) —
  all SOP-recommended, no custom protocol or HTTP-client code.
- **New dependencies**: `fastmcp`, `httpx`, `pydantic-settings` — the SOP's standard stack for every
  MCP repo in this org; no additional third-party SDK needed since the vendor API is plain JSON-RPC
  over HTTP.
- **New API/tool shape**: ten tools under the `bitdefender_` prefix, listed above; each tool's
  request/response shape mirrors the corresponding GravityZone JSON-RPC method's `params`/`result`,
  narrowed to the fields an agent needs (ids, names, status, priority) rather than mirroring every
  vendor field.
- **In-scope cleanup**: none — the repo has no prior code.
- **Follow-ups (out of this ticket's scope, list for a future ticket if asked for)**: company/
  license/account administration, custom endpoint groups, scan-task scheduling, quarantine
  management, push/webhook configuration, and policy authoring/assignment if GravityZone later
  exposes a documented method for it.

### Data & API contract

Request/response shape (example — `bitdefender_list_incidents`):

```json
// tool call params
{"page": 1, "per_page": 50}

// tool result (compact JSON string, matches GravityZone's own envelope shape)
{"page": 1, "pages_count": 3, "per_page": 50, "total": 112,
 "items": [{"id": "5f7c...", "name": "Ransomware detected on WIN-DESKTOP-01",
            "priority": "high", "status": "open"}]}
```

Error envelope (uniform across all ten tools):

```json
{"error": {"code": "unauthorized", "message": "GravityZone rejected the API key", "retryable": false}}
```

| GravityZone signal | `code` |
|---|---|
| missing `X-Bitdefender-Api-Key` header | `not_configured` |
| HTTP 401 | `unauthorized` |
| HTTP 403 | `unauthorized` |
| JSON-RPC `-32601 Method not found` on an id that doesn't exist | `not_found` |
| JSON-RPC `-32602 Invalid params` / `-32600 Invalid Request` | `invalid_argument` |
| HTTP 429 | `rate_limited` |
| JSON-RPC `-32000 Server error` / `-32700 Parse error` / network timeout | `upstream_error` |

No DB, no migration — this service has no persistent store.

### Key flow / sequence

```
Agent -> Gateway -> bitdefender-mcp /mcp (X-Bitdefender-Api-Key, X-Bitdefender-Base-Url)
  -> middleware: set contextvar(api_key, base_url) for this request
  -> tool handler: build JSON-RPC {jsonrpc:"2.0", id, method, params}
  -> httpx POST {base_url}/v1.0/jsonrpc/<service>, Authorization: Basic base64(api_key:)
  -> GravityZone Control Center
  <- JSON-RPC result or error
  -> errors.py maps vendor error -> structured envelope (on error)
  -> tool returns compact JSON string
  -> middleware: reset contextvar (finally)
```

### Non-functional

- **Multi-tenant isolation**: one container serves many tenants concurrently; credentials and the
  per-tenant base URL live only in a `contextvars.ContextVar` set at the top of the request and
  `reset()` in a `finally` block — never a module-level variable, never cached across requests (AC13).
- **Performance**: outbound connect timeout 5s, read timeout 30s; bounded retry (max 3 attempts) on
  429/5xx honoring `Retry-After`; total time per tool call capped under 120s (SOP §5); a single
  `httpx.AsyncClient` reused within one request's lifetime, not across requests.
- **Rate limiting**: GravityZone allows 10 req/s per API key (AC14); the client backs off on 429
  rather than hammering the vendor, and surfaces `rate_limited` once retries are exhausted rather
  than blocking indefinitely.
- **Security**: credential only ever appears in the `Authorization` header sent to GravityZone, never
  logged, never persisted; `gitleaks detect` run before delivery; no vendor name/brand appears
  outside README and user-facing tool descriptions per SOP §0.4.
- **Observability**: structured log line per tool call (tool name, GravityZone method, status code,
  duration) with the API key redacted.

### Rollout & rollback

New repo, first version: push directly to `main` (SOP A2 — no `dev-lock` needed for a repo nobody
else is using yet), then call `/api/vendor-register` (not `/api/deploy-int` — the gateway does not

### Decisions made by DEV01

- **Credential headers**: `X-Bitdefender-Api-Key` (required) + `X-Bitdefender-Base-Url` (optional,
  defaults to the Bitdefender cloud Access URL) — why: the vendor's own API Guide treats the Access
  URL as per-tenant from page 2 onward (on-prem Control Center installs use a different host);
  alternative considered: hardcode the cloud URL only, rejected because it would silently break
  on-prem GravityZone tenants, which are common in the MSP space this platform serves.
- **v1 tool scope**: policies + endpoints (read-only) and incidents (read + priority/assignment
  triage + isolate/restore) — why: this is the literal reading of "manage endpoint protection
  policies and review security events"; alternative considered: cover the full GravityZone API
  surface (companies, licensing, packages, quarantine, push/webhooks) in v1, rejected for tool-count
  discipline (SOP: tools are capabilities, not an endpoint mirror, ≤20 per service) and because
  nothing in the ticket asks for console-administration capabilities.
- **No policy-assignment tool**: GravityZone's confirmed public API only documents
  `getPoliciesList`/`getPolicyDetails` for policies; no assign-policy-to-endpoint method is in the
  2019 API Guide. Alternative considered: implement assignment against an undocumented/guessed
  method name — rejected as unsafe (wrong method name would silently fail or do the wrong thing on a
  security product). If this capability is needed, it should come back as a named gap per
  `mcp-track.md` 2.1.
- **Rate-limit handling**: client-side bounded retry with backoff honoring `Retry-After`, mapped to
  `rate_limited` once exhausted — why: the vendor hard-enforces 10 req/s per key (429 on excess);
  alternative considered: let 429s surface raw as `upstream_error` — rejected because `rate_limited`
  is the correct, more actionable `code` per the SOP's fixed vocabulary.
- **Pagination**: pass through GravityZone's own `page`/`perPage` with `per_page` capped at 200 —
  why: matches the vendor's own list-response shape 1:1 (`page`, `pagesCount`, `perPage`, `total`,
  `items`), avoiding a second incompatible pagination convention.

  `destructiveHint`.

  on a previously isolated endpoint creates a restore task and returns its task id.
- **TC13 · AC11 · auto** — any `bitdefender_*` tool called with no `X-Bitdefender-Api-Key` header

  is mapped to `{"error": {"code": "invalid_argument", ...}}`; a mocked HTTP 429 is mapped to
  `{"error": {"code": "rate_limited", ...}}`.
- **TC15 · AC13 · auto** — two concurrent requests using two different `X-Bitdefender-Api-Key`
  values each receive only their own mocked response; the contextvar for request A is never visible
  while handling request B.
- **TC16 · AC14 · auto** — a mocked sequence of 429 responses followed by a 200 triggers the bounded

  configured cap.
